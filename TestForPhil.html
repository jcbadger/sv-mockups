ShareVault Root Cause Analysis Training, V3, 2026

Stop treating symptoms.
Fix the cause.

Every unresolved root cause creates a bug burden that compounds. This training walks through ShareVault's 8-step RCA process so you can apply it consistently — and so every analysis we produce holds up to audit.

When do we do an RCA?

We can't analyze every bug — we triage by risk. RCA is required for:

🔁
Repeat offenders
Bugs in core functions that keep coming back — degradation issues and regression patterns.
⚠️
Untouched code that broke
Core functions outside new features that broke without being directly modified.
🔐
Security & compliance issues
Any issue that implicates access controls, data integrity, or audit requirements.
🔥
Production incidents
Customer-impacting outages or degradations that required emergency response.

Step 1 of 8

Define the Problem

📋 Start with the right Jira ticket type. If the issue is complex, attach the RCA worksheet.

What belongs in the problem statement

  • Expected behavior vs. observed behavior (or observed symptoms)
  • Direct and indirect impact — who is affected and how
  • Stakeholders involved and consequences of not fixing it
  • Scope: how widespread is the problem?

🚫 What does NOT belong in the problem statement

❌ Suspected root cause
"The bug happened because the cache wasn't cleared."
❌ Proposed solution
"We need to add a cache-busting header."
❌ "We need to…"
Action items belong in Steps 5–6, not the problem definition.

Example: Good vs. Poor Problem Statements

✅ Good

"Admin permission edits for vaults with >500 files take over 30 seconds to respond. Expected response is under 3 seconds. Affects all TMF admins. Customer-reported, reproduced in prod."

❌ Poor

"Vault is slow. We need to fix the database query and add indexing."

Step 2 of 8

Collect the Data

Evidence drives analysis. Collect everything that establishes context, scope, and history before drawing conclusions.

Data collection checklist

  • Screenshots, screen recordings, or error messages showing the problem
  • Event logs from the time of the incident — post them directly in the ticket
  • Exact timestamp: when did this start?
  • What else was happening at that time? (deployments, config changes, vendor issues)
  • Has this happened before? If yes, link the previous ticket and its resolution
  • Links to related bug reports or support cases
  • Scope: how many users, vaults, or transactions are affected?

Key questions to answer in the ticket

🕐
When did this start?
Exact date/time, not "recently"
🔄
Is this a repeat?
Link previous analysis if it's recurred
🌐
What was going on?
Concurrent changes, deployments, incidents
📏
What's the scope?
Specific users vs. all users, prod vs. staging
Step 3 of 8

Identify Possible Causal or Contributing Factors

Before identifying the root cause, list all possible contributing factors. Cast wide, then narrow.

What changed?

Start by examining every dimension of change around the time of the incident.

💻
Code
⚙️
Configuration
🖥️
Server / Infra
📐
Design / Schema
📋
Process / Procedure
👤
Human Action

Build your causal factor list

  • Trace the chain of events leading to the problem
  • Identify where boundaries changed (e.g., new data volumes, new vendor behavior)
  • Identify controls that were in place — did any fail?
  • Was there a human action that contributed? (configuration, deployment, response)
  • Look for underlying contributing factors below the obvious surface causes
  • Document everything in the Jira ticket or the attached RCA worksheet
💡 Fault Tree tip: Start from the problem at the top and work downward. For each event, ask "what could cause this?" and branch out. List all branches before narrowing to root causes in Step 4.
Step 4 of 8

Identify Root Cause(s)

From your causal factor list, find the deepest points in the event chain. Use the 5 Whys technique: ask "why?" repeatedly until you reach the systemic source.

📌 Simple problems may have a single root cause. Repeat problems almost always require deeper inspection. Complex issues often have multiple contributing root causes.

Step 5 of 8

Recommendations

Don't stop at one fix. Generate multiple options and evaluate them — the best solution may not be the most obvious one.

Generate multiple options

Root causes are often process problems that surface as technical failures. Solutions may need to address multiple layers:

🔧
Repair / Patch
Restores function quickly — but does not address the root cause on its own.
📋
Process change
Modifies how we do things — often the real fix when root cause is procedural.
🛡️
Compensating / preventive controls
Monitoring, alerting, port filtering — reduces blast radius or detects early.
🧑‍🏫
Training / policy change
Addresses human behavior root causes — includes updating playbooks and runbooks.
⚠️ Both technical and non-technical recommendations must be entered into Jira. Do not leave any recommendation as a verbal agreement or a Slack message.
Step 6 of 8

Solutions in Jira

Selecting and documenting the solution is as important as finding the root cause. Every decision must be traceable in Jira.

Jira documentation requirements

BUG SV-XXXX · Root Cause Analysis
Root Cause panel
All root causes documented here, or linked from here
Corrective Actions
Summary of all recommendations from Step 5
Selected solution
Most viable option(s) chosen based on ROI. Rationale documented.
Sub-tickets
Created as needed for individual corrective actions, linked back to this ticket
Issue Type (sub)
Set to "Corrective" — required for audit trail
Ticket status
Cannot close until root cause is documented
💡 Production issues require a repair to restore function quickly — but the ticket cannot be closed until root cause analysis is complete and documented.
Step 7 of 8

Test & Validate

🔍 Audit requirement: All validation activity is subject to audit. Document everything in Jira.
  • All Jira tickets have a workflow to QA — use it
  • QA verifies both technical fixes and non-technical changes (process, training, policy)
  • Non-technical changes with compliance implications go through risk assessment
  • Create a Jira Issue Type "Corrective" for each verified change
  • Every Corrective ticket links back to the original RCA ticket

What QA is verifying

Technical changes
The fix resolves the originally reported behavior. Regression test for related functions. No new issues introduced.
Non-technical changes
Process or policy change is documented and communicated. Training has occurred. Playbooks are updated.
Step 8 of 8

Continually Improve

🔍 Audit requirement: Improvements are key to the future of the company and will be audited.

A closed bug is not an improved system. Every major issue should leave us better than before — not just restored to the previous state.

  • Any major issue that goes beyond "restore to previous state" is tracked as an improvement
  • Improvement entered in Jira as Issue Type "Corrective"
  • All improvement tickets link back to the original RCA ticket
  • Improvements are reviewed for patterns — repeat root causes signal systemic gaps

Ask after every RCA:

🔁
Could a process change prevent this class of problem from recurring?
📚
Does our runbook / playbook need updating based on what we learned?
🔔
Do we have monitoring or alerting that would have caught this earlier?
🧑‍💻
Is there a single point of failure (person or vendor) this exposed?

SV-9083 — Cloudflare Outage Response
Production
Context: During a Cloudflare incident, users were impacted but received no proper error display. Support had no accurate information to give customers. The DR solution deployed degraded service further.
5 Whys

Root causes identified in original review:

  • Error page was in Cloudflare — no fallback when www.sharevault.net is unreachable
  • DR process repurposed the outage page, blocking proper routing
  • Mass redirect to error page was impractical since not all users were affected
  • Support was not informed in time and had no playbook for a newly discovered outage
  • CloudFlare is a SPOF (single point of failure) vendor
Incident
SV-8654 — CloudFlare Bypass Outage
Production
Context: Extended outage involving CloudFlare. Support had no valid answers for customers. Monitoring was delayed. Work was coordinated over cell phone instead of Zoom. UptimeRobot account had been deleted. CloudFlare restoration was delayed due to vendor uncertainty. DevOps was a SPOF due to limited availability.
5 Whys — Focus: Why did Support have no valid answers to give customers?
Show reference analysis ▾

Key lessons from original review:

  • Support was not informed timely — no escalation process for newly discovered outages
  • Monitoring and feedback loop failed to trigger promptly
  • Coordination happened over cell phone — not a proper incident channel
  • Playbook list and content incomplete for this scenario
  • CloudFlare is a SPOF vendor — no bypass plan was validated
  • DevOps SPOF — limited availability during incident
  • UptimeRobot account deleted and not transitioned — email notification was missed
Incident
SV-9115 — Vault Permission Editing Performance
Production
Context: A customer reported extremely slow admin permission editing. The ShareVault team observed 30+ second response times while on a screenshare with a new TMF admin editing vault "Momentum AXS 07 301" (SVid 5156). Engineering confirmed the issue: an incorrect value was passed and the server could not parse it. Three developers and one week were required to fix it.
5 Whys — Focus: Why did the permission edit take 30+ seconds?
Show reference analysis ▾

Key findings:

  • An incorrect value was passed to the server — server could not parse it, causing a timeout loop
  • No input validation caught the malformed value before it hit the server
  • No timeout or graceful failure path existed for this code path
  • The bug required 3 developers and a week to resolve — suggesting inadequate test coverage for permission editing with edge-case data
  • Jira ticket was initially submitted with insufficient detail, delaying diagnosis
